 Source: POST generate contract template (Confluence, Phoenix space) Generated: 2025-03-17 Environment System: Phoenix API: Generate contract document (PDF) from template for a product contract &mdash; for use by Sales Portal / Energy Portal Consumers: Energo-Pro Sales portal, Energo-Pro Energy portal (customer selects product; portal calls Phoenix to get the contract document for checking, validation, and signing on device) Task for: Backend (Phoenix API), integration with portals User story (business) As a customer of Energo-Pro Sales or Energo-Pro Energy services, I want to be able to get the contract document for the product of my choice, So that I can check, validate, and easily sign it on my device. Business flow (trigger & outcome) The trigger is the Sales or Energy portal sending a POST request with the selected product identifier, product version, and the contract data (JSON). Outcome: Phoenix resolves the product contract and version, finds the template attached to that product version whose name starts with the string &quot;CSP&quot; (Customer Sales Portal). If there is no such template &rarr; return null (no document); if there is more than one such template &rarr; return error ; otherwise Phoenix generates the PDF according to the Phoenix template and returns the generated file, named according to the settings in the Phoenix template object. Logical conditions (filtering terms) Template selection is governed by the following conditions. All logic is defined in this spec; no external file references. ID Condition Description LC-T1 Include only templates whose name starts with &quot;CSP&quot; From the templates attached to the selected Product version, consider only those whose name (e.g. template detail name) starts with the string &quot;CSP&quot; . Any other templates are ignored for this API. LC-T2 Exactly one CSP template required for generation For the API to generate a document: there must be exactly one template matching LC-T1. If zero match &rarr; do not generate; return null (e.g. HTTP 404 or 204). If more than one match &rarr; do not generate; return error (e.g. HTTP 400 with a clear message). LC-F1 Filename from Phoenix template object The generated file name must be built according to the Phoenix template object settings (e.g. template detail: file name prefix, file name parts, file name suffix, as used in existing product contract document generation). Logic description Request validations must be applied at the validation layer (e.g. DTO with Jakarta Bean Validation). Invalid or missing parameters result in HTTP 400 with a per-field error message (see Validation error messages in Technical details). Input: Phoenix receives Product_ID (product contract id), Product_Version (version id), and ContractJSON (contract data in the same structure as used in Phoenix for contract document model). Resolve product contract and version: Load product contract by id and product contract details by (contract id, version id). If not found or status not valid for generation &rarr; return HTTP 404 (or project-agreed response). All behaviour and validation are based on Phoenix (API, backend, DB); no dependency on external systems for core logic. Template selection: From the templates attached to the given Product version , apply LC-T1 : keep only templates whose name starts with &quot;CSP&quot; . Then apply LC-T2 : if zero such templates &rarr; return null (e.g. 404 No CSP template found); if more than one &rarr; return error (e.g. 400 Multiple CSP templates found; only one allowed); if exactly one &rarr; use that template for generation. Document generation: Using the selected template and the provided ContractJSON , Phoenix generates the contract document (PDF) as per existing document generation logic (e.g. DocumentGenerationService , template file, contract document model). The request body ContractJSON is mapped to the same structure Phoenix uses internally for filling the template (e.g. ContractDocumentModel or equivalent); structure must align with Phoenix so that placeholders in the template are correctly replaced. Response: Return the generated PDF as binary with Content-Disposition (or equivalent) so the filename is as per LC-F1 (Phoenix template object settings: prefix, name parts, suffix). Do not return pagination; this is a single file response. Edge cases: Invalid product/version &rarr; 404; no CSP template &rarr; 404 (or 204); multiple CSP templates &rarr; 400; validation failure on body &rarr; 400; server error &rarr; 5xx. Request description Method and path: POST /contract/template (or as per Phoenix API convention, e.g. /api/.../contract/template ). Headers: As per Phoenix API standards (e.g. Content-Type: application/json; authentication as per integration agreement with Sales/Energy portal). Body: JSON object with product contract identifier, product version, and contract data. Parameter Type Required Description productId number (long) Yes Product contract ID in Phoenix. productVersion integer Yes Product contract version ID. contractJson object Yes Contract data in the same structure as in Phoenix used for filling the contract template (e.g. map to ContractDocumentModel or the structure consumed by existing document generation). Full request body (JSON): Property Type Required Description productId long Yes Product contract ID. productVersion integer Yes Product contract version ID. contractJson object Yes Contract data; structure must match Phoenix document model so the template can be filled correctly. Example (minimal): wide 760 (The actual shape of contractJson must match the Phoenix contract document model used by DocumentGenerationService / product contract document creation; define or reference the exact schema in the implementation.) Response description Success: HTTP 200 with binary PDF body. Response headers must include Content-Type: application/pdf and Content-Disposition with the filename built according to the Phoenix template object settings (LC-F1). No CSP template: When zero templates match LC-T1 &rarr; HTTP 404 (or 204 No Content) with an optional message (e.g. &quot;No CSP template found for this product version&quot;). Multiple CSP templates: When more than one template matches LC-T1 &rarr; HTTP 400 with a clear error message (e.g. &quot;Multiple CSP templates found; exactly one required&quot;). Not found / invalid: Product contract or version not found or not valid for generation &rarr; HTTP 404 . Client error: Validation failures (missing/invalid productId, productVersion, or contractJson) &rarr; HTTP 400 with per-field error messages (see Validation error messages ). Server error: HTTP 5xx for unexpected failures. Response is not paginated and not JSON; it is a single binary file. Pagination metadata is not applicable. Acceptance criteria Given a valid request (existing product contract id, version id, valid contractJson): when exactly one template attached to that product version has a name starting with &quot;CSP&quot;, the API returns 200 with the generated PDF and correct filename in Content-Disposition. Given a valid product/version but no template whose name starts with &quot;CSP&quot;: the API returns 404 (or 204) and does not generate a file. Given a valid product/version but more than one template whose name starts with &quot;CSP&quot;: the API returns 400 with a message indicating multiple CSP templates. Given missing or invalid productId or productVersion : the API returns 400 with distinct validation messages (see Validation error messages). Given productId / productVersion that do not exist or are not valid for generation: the API returns 404 . Given invalid or missing contractJson (e.g. required fields for document model): the API returns 400 with appropriate validation message. The generated file name matches the Phoenix template object settings (prefix, name parts, suffix) for the selected CSP template.
