The primary objective of this system is to ensure the correct conclusion of the billing process. The billing procedure will take into consideration data derived from contracts and orders. Consequently, both of these components are essential for the correct execution of the process. To create a contract or an order, it is mandatory to define its parameters in accordance with the product, service, and goods objects.

 

The process of creating a price component within Bundle 2 involves gathering of essential information to establish the price parameters accurately for the product and service in order to create its contract correctly.

 

The price component, an integral element of Bundle 2, combines a comprehensive definition of its parameters and details. Within the Phoenix system, the term 'price component' pertains to the definition of pricing and its associated parameters for products and services.

 

The price component object is structured into two distinct tabs, and each contains its mandatory aspects:

  1. General settings tab: This tab serves for defining the general attributes of the price component and specifying pricing details under various conditions. Logics of the fields:

    1. Name related fields: it is mandatory to define names for the price component itself and for related invoices and templated.

    2. Price type: the specification of the price type is essential to ensure accurate calculations in billing.

    3. Value type: defining the value type of the price component through the nomenclature is mandatory for connected calculations in billing. It is also mandatory to define currency and the number type (positive or negative) for the same reason.

    4. VAT rate: the VAT rate for the price component must be defined to apply this additional tax to the customer.

    5. Income account and Cost center / Controlling order: while these fields are optional, if included in the price component, they should match corresponding fields in the product or service to make accurate calculations. If there fields are defined in the price component but are left unfilled in the  product or service, they should become mandatory fields in the product and service.

    6. Visualization tab for contract template: this is an optional field intended to provide additional comments while to contract template incorporate this price component.

    7. Formula option: the system allows to definition of prices in the first tab using formulas. Additionally, it permits the specification of values and their ranges for the price component when necessary.

    8. Conditions: the system also supports the definition of conditions for the price component. For example, if the customer type is selected as a legal entity in the condition and a user attempts to create a contract with this price component for  private customer, the system should not allow it.

    9. Price in words: it is possible to define the price using words and specify in which invoice to display this information.

  2. Application model tab: this tab defines the logic by which the system calculated the price. It consists of the following mandatory elements:

    1. Application model type: it is mandatory to select the application model type that the system will use for price calculations in billing (e.g., volumes, over price, or per price)

    2. Application type: it is mandatory to define the application type as either by settlement period or by scales to align with the correct Point of Delivery while calculating the invoice in billing.

      1. If settlement period is chosen, this indicated that the price component should be created we a defined time period.

      2. If scale is chosen, this implies that the price component should be created using scales nomenclature to define the price based on the pre-defined scales.

    3. Restrictions: these restriction establish minimum and maximum amounts, predefining the range in which this price component should be used. For example, if the maximum volume amount is set at 200 kWh, it means that this price component is applicable for volumes exceeding 20 kWh for price determination.

 

 

During price component creation:

  • When creating a price component, completion of all required fields on both tabs is mandatory.

    • After clicking the 'Create' button, the system should check frontend validation, and if an error is detected, it should be displayed in the proper field.

    • In the event of a backend error (after successful frontend validation), the system also displays an error message.

 

During price component editing:

  • Price component does not include versioning functionality and only one version of the price component should be created.

  • If a price component is already included in a contract or order, editing without 'Edit Locked' permission is not possible. 

  • It is possible to change all the fields parameters in the editing mode.
