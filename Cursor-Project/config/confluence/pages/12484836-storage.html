POD-based Pricing Variables for Product Contract Price Components

As a system user
I want to use two POD-based contract variables in Product Contract price component formulas
So that pricing can automatically adjust based on the number of PODs linked to the contract and their activity in the billing month.

Business Need

Pricing formulas need additional contract-related POD metrics to support more flexible pricing logic.
Two new variables must be introduced in the formula builder and controlled by usage conditions to prevent invalid formula configurations.

Variables to Introduce

  1. nPODa — Num Active PODs in contract
    Number of PODs linked to the priced Product Contract version that were active for at least one day during the month taken from the Max End Date from the billing run.

  2. nPOD — Total Num PODs in contract
    Total number of PODs linked to the priced Product Contract version, regardless of activity status.

Conditional Usage Rule (Important)

These variables must be usable only when Price Component Application Model Type = With Electricity Invoice.

If Application Model Type is anything else, the system must:

  • prevent use of nPODa and nPOD in formula

  • display validation error

  • block saving until invalid variables are removed

This ensures formulas with these variables are not used in unsupported billing scenarios.

 

Acceptance Criteria

  1. Variable availability in formula builder

    • System displays two new variables in Price Component formula builder:

      • nPODa — Num Active PODs in contract

      • nPOD — Total Num PODs in contract

    • Variables are available for Product Contract pricing formulas.

  2. Variable definitions are consistent

    • nPODa is evaluated as count of PODs linked to the priced Product Contract version that overlap at least one day with the month derived from the maximum End Date of the billing run.

    • nPOD is evaluated as total count of PODs linked to the priced Product Contract version, regardless of activity status.

  3. Usage in formulas

    • System allows nPODa and nPOD to be used in supported formula expressions (numeric operations and conditional expressions where supported).

    • Existing formula parsing and validation behavior applies to these variables as to all numeric variables.

  4. Application Model restriction

    • Variables nPODa and nPOD are allowed only when Price Component Application Model Type = With Electricity Invoice.

    • If Application Model Type is not With Electricity Invoice, system must treat usage of nPODa/nPOD as invalid.

  5. Validation and save blocking

    • When formula contains nPODa or nPOD and Application Model Type != With Electricity Invoice, system:

      • displays validation error,

      • prevents formula save,

      • keeps save blocked until restricted variables are removed or Application Model Type is changed to With Electricity Invoice.

  6. Validation timing

    • Restriction is enforced at formula builder/save stage (before Billing Run creation/execution).

  7. Error message clarity

    • Validation message clearly states that nPODa and nPOD are supported only for Price Components with Application Model Type With Electricity Invoice.

  8. Backward compatibility

    • Existing formulas that do not use nPODa/nPOD remain unaffected.

    • Existing behavior for all other variables remains unchanged.

  9. Edge-case support for evaluated values

    • Formula evaluation supports at least these values for both variables without runtime failure:

      • 0

      • 1

      • higher values relevant for tier boundaries (e.g., 4/5/6).
