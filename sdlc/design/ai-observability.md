# AI დაკვირვება (observability) — სტრუქტურა v0

> **სტატუსი:** ჩარჩო; სტეკი Phase 9-ში შეირჩევა. აქ აღწერილია, რას ვაკვირდებით და რა ფორმით ვწერთ აგენტის ლოგებს.

## 1. რატომ

როცა აგენტი ავტონომიურად მუშაობს, ყოველ ნაბიჯს ვეღარ უყურებ. Observability ნიშნავს, რომ ნებისმიერ დროს შეგიძლია უპასუხო კითხვებს: რა გააკეთა აგენტმა? რატომ? რა დაჯდა? რამე ხომ არ გაფუჭდა? ვინ დაამტკიცა?

## 2. ორი დაკვირვების ობიექტი

1. **Cursor-ის აგენტი (მშენებელი)** — სესიები, ხელსაწყოების გამოძახებები, ქვეაგენტები და მათი მოდელები, hook-ების ვერდიქტები, ხარჯი.
2. **პროდუქტის აგენტი** (თუ ასეთი იქნება) — მომხმარებლის მოთხოვნები, მოდელის გამოძახებები, ხელსაწყოები, შედეგები.

## 4. მოვლენის სქემა — აგენტის ლოგის ფორმა

ყოველი ჩანაწერი ერთი JSON ხაზია (JSONL ფორმატი):

```json
{
  "ts": "2026-10-06T12:00:00Z",
  "session_id": "…",
  "turn_id": "…",
  "actor": "coder | advisor | auditor | verifier | architect | owner | product-agent",
  "event": "session_start | prompt | model_call | tool_call | guard_verdict | decision | gate | error | session_end",
  "phase": "6-build",
  "tool": "Bash",
  "input_summary": "<redacted short summary>",
  "outcome": "ok | blocked | failed | inconclusive",
  "reason": "…",
  "tokens_in": 0,
  "tokens_out": 0,
  "cost_usd": 0.0,
  "duration_ms": 0,
  "artifact": "docs/plan.md @ <commit>",
  "approved_by": "owner | —"
}
```

ლოგში არასდროს იწერება საიდუმლოებები, ტოკენები ან პერსონალური მონაცემები; რედაქცია ჩაწერამდე ხდება. ეს სქემა OpenTelemetry-ის GenAI ტრადიციებს მიჰყვება, რათა მოგვიანებით ნებისმიერ სტეკში გადაიტანო.

## 5. საკონტროლო ზოლები (control bands) — playbook-ის Maintain ეტაპიდან

დეტერმინისტული სკრიპტი ერთ მეტრიკას უყურებს მოძრავი საბაზისო მნიშვნელობით (საშუალო ± σ). წესები (მაგ. Western Electric) იჭერენ როგორც უეცარ ნახტომს, ისე ნელ დრიფტს. რეაგირება დონეებადაა დაყოფილი: 1σ — მხოლოდ ჟურნალში ჩაწერა; 2σ — Claude დიაგნოზს სვამს მხოლოდ კითხვის უფლებით; 3σ — Claude გასწორებას PR-ით ან წინასწარ დამტკიცებული runbook-ით (მოქმედების ინსტრუქციით) სთავაზობს. დიაგნოზი ახალ intent.md-ად იწერება და ციკლი თავიდან იწყება. თავად აღმოჩენაში მოდელი არ მონაწილეობს.

მეტრიკების კანდიდატები: evals-ის გავლის მაჩვენებელი, დღიური ხარჯი, შეცდომების მაჩვენებელი, PR-ის ციკლის დრო.

## 6. რას ვზომავთ ძრავისთვის (playbook-ის ინდიკატორები)

- **წინმსწრები (leading):** დრო intent-იდან spec-მდე და spec-იდან plan-მდე (git-ის დროის ნიშნულებით); დავალებების წილი, რომლებიც პირველივე CHECK-ზე მწვანდება; review-ის სისწრაფე.
- **შედეგობრივი (lagging):** გადაკეთება (spec-ის commit-ები პირველი plan-ის commit-ის შემდეგ); ხარვეზები, რომლებიც დემოზე აღმოჩნდა, აუდიტორის აღმოჩენილებთან შედარებით; განმეორებული შეცდომები (`tasks/lessons.md`).

## 7. რაც უკვე აწყობილია (ADR-0006, ADR-0008)

მშენებლის, ანუ თავად Cursor-ის აგენტის, დაკვირვება პირველივე დღიდან მუშაობს. `.cursor/hooks/cursor_adapter.py` (`event_log.py`-ით) ყოველ ხელსაწყოს გამოძახებას და ყოველ ქვეაგენტს ერთ ხაზად წერს `.cursor/logs/events-<თარიღი>.jsonl`-ში: დრო, სესია, აგენტი (main / auditor / verifier …), ხელსაწყო, მოკლე აღწერა (200 სიმბოლომდე; დაფარულია ცნობილი სერვისების გასაღებები, Bearer / Authorization მნიშვნელობები, `password=…` ტიპის ჩანაწერები (ბრჭყალებში და JSON-შიც) და პაროლი URL-ში — სხვა ფორმის საიდუმლო შეიძლება გაიპაროს), შედეგი (ok / failed) და მოდელი. `python3 sdlc/checks/agent_report.py` ამ ჟურნალს აჯამებს და ამბობს, რომელი ქვეაგენტი რომელ მოდელზე იმუშავა; ტოკენებს და ხარჯს Cursor-ის usage დაფა აჩვენებს. ეს §4-ის სქემის მსუბუქი ქვესიმრავლეა. **ცნობილი ზღვარი:** hook-ის მიერ დაბლოკილი გამოძახებები postToolUse-მდე არ აღწევს, ამიტომ ჟურნალში არ ჩანს.

## 8. ვარიანტები Phase 9-ისთვის (წინასწარი)

- **A — მსუბუქი:** OpenTelemetry → ლოკალური ფაილი ან console + agentsview + ჩვენი JSONL სქემა.
- **B — საშუალო:** OpenTelemetry → ლოკალური collector (Docker) + Prometheus / Grafana.
- **C — პროდუქტის აგენტისთვის:** Langfuse (trace-ები + evals + ხარჯი).
