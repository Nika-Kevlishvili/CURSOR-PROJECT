## 3. ჩამოტვირთვა და გახსნა Cursor-ში

```bash
git clone https://github.com/tornikebolokadze1-cyber/Asterbit.git
cd Asterbit
```

1. File → Open Folder → აირჩიე თავად `Asterbit` საქაღალდე და არა ის, რომელშიც ის დევს. სხვაგვარად Cursor `.cursor/hooks.json`-ს, `.cursor/agents/`-სა და `.cursor/skills/`-ს ვერ იპოვის და დაცვა არ ჩაირთვება.
2. როცა Cursor საქაღალდის ნდობას გკითხავს, უპასუხე „კი" (hook-ები მხოლოდ სანდო საქაღალდეში ეშვება).
3. მოდელის არჩევანში აირჩიე **Claude Sonnet 5.5** (effort high) — ეს კოდერის როლია (ADR-0007). Cursor-ში ამას რეპო ვერ აფიქსირებს; სხვა მოდელის შემთხვევაში აგენტი პირველივე პასუხში გეტყვის.
4. შეამოწმე, რომ hook-ები ჩაიტვირთა: Customize → Hooks ან Output → Hooks. მერე ჩაწერე `/sdlc-status` — აგენტი გეტყვის მიმდინარე ეტაპს და შემდეგ ნაბიჯს.
5. თუ შენს კომპიუტერზე Claude Code-ის გლობალური hook-ები გაქვს (`~/.claude/settings.json`), Cursor მათაც გაუშვებს, სანამ Settings → Agents → Third-Party Imports ჩართულია. ამ რეპოს ისინი არ სჭირდება; თუ ხელს გიშლის, ეს პარამეტრი გამორთე.

## 4. როგორ შევიტანოთ ცვლილება

`main` პროექტის მთავარი ვერსიაა. მასში პირდაპირ არავინ წერს — არც მფლობელი და არც აგენტი. ყოველი ცვლილება ასე მიდის:

```bash
git switch main && git pull          # 1. უახლესი ვერსია
git switch -c docs/my-change         # 2. ახალი branch, ლათინური სახელით (feat/, fix/, docs/, chore/)
# 3. ცვლილება — ხელით ან აგენტით
git add README.md docs/FILES.md      # 4. ფაილები სახელით, არა `git add -A`
git commit -m "docs: რა შეიცვალა"
git push -u origin docs/my-change    # 5. ატვირთვა
gh pr create --fill                  # 6. PR (ან GitHub-ის საიტიდან)
```

`git add -A`-ს იმიტომ ვერიდებით, რომ ის plugin-ების დროებით ფაილებსაც იჭერს; ერთხელ ასე უკვე მოხდა (იხ. [tasks/lessons.md](tasks/lessons.md)).

PR-ს მფლობელი განიხილავს და `main`-ში თვითონ აერთიანებს. რეპო 2026-10-08-დან public-ია, ამიტომ `main`-ის დაცვა (branch protection) GitHub-ის უფასო გეგმაზეც ირთვება — ჩართვა მფლობელის გადასაწყვეტია. სანამ ის არ ჩაირთვება, ეს წესი შეთანხმებაზე დგას და არა ტექნიკურ აკრძალვაზე.

## 6. უსაფრთხოება — რა გვაქვს და რა ჯერ არა

პროექტს საკუთარი ავტომატური დაცვა აქვს, რომელიც რეპოსთან ერთად ჩამოდის: `.cursor/hooks.json` და `.cursor/hooks/` (hook-ები — ავტომატური ჩამრთველები, რომლებიც სახიფათო მოქმედებას ბლოკავს; [ADR-0005](docs/decisions/0005-harness-v0.md), [ADR-0008](docs/decisions/0008-cursor-support.md)). აგენტი ფაილებს რეპოში თავისით ასწორებს და სამუშაო branch-ს თავისით ტვირთავს. hook-ები ბლოკავს: `rm -rf`-ს, `git reset --hard`-ს, `git clean -f`-ს, force-push-ს, `main`-ში push-ს, `--no-verify`-ს, საიდუმლო ფაილების წაკითხვას, ჩაწერასა და ქსელით გაგზავნას; ჯერ გკითხავს (Cursor-ის დასტურის ფანჯრით) შეუნახავი სამუშაოს ან branch-ის წამშლელ ბრძანებებზე (`switch -f`, `restore`, `branch -D`, `stash drop`), პროგრამის დაყენებაზე (`pip`, `npm`, `brew`, `npx`), ინტერნეტიდან ჩამოტვირთვაზე (`curl`, `wget`) და PR-ის გაერთიანებაზე; commit-მდე staged ცვლილებებს საიდუმლოებებზე ამოწმებს. ამიტომ აგენტი ჯერ `git add`-ს უშვებს და მერე, ცალკე, `git commit`-ს. auditor, verifier, architect, scout და advisor ფაილებს ვერ ცვლიან. თუ hook რამეს დაბლოკავს, აგენტი აგიხსნის, რატომ — hook-ს გვერდს ნუ აუვლი. ყოველ PR-ზე GitHub იგივე შემოწმებებს თავადაც უშვებს (CI) და მწვანე ან წითელ ნიშანს აჩვენებს.

რა ჯერ არა: Cursor-ის hook ფაილის ცვლილებაზე მხოლოდ „დაშვება" ან „აკრძალვა" შეუძლია და „იკითხე" არა, ამიტომ `.cursor/hooks.json`-ის, `.cursor/hooks/`-ისა და CI-ის შეცვლამდე შენი (მფლობელის) თანხმობა წესზე და PR-ის განხილვაზე დგას და არა hook-ზე. ინტერნეტის გვერდების წაკითხვას (WebFetch) Cursor-ის საკუთარი დასტურის პარამეტრები მართავს. Cursor აგენტს `.cursorignore`-ის ჩაწერის უფლებას არ აძლევს, ამიტომ თუ დამატებითი დაცვა გინდა, ეს ფაილი თავად შექმენი რეპოს ძირში — შიგნით `.gitignore`-ის საიდუმლოებების სია ჩაწერე (`.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `credentials.json`, `serviceAccountKey.json`, `secrets/`). `.env*` Cursor-ს ნაგულისხმევადაც დამალული აქვს.

hook-ები აგენტის მოქმედებებს იცავს. თუ ბრძანებას ხელით უშვებ, სამი წესი შენზეა:

- საიდუმლოება (პაროლი, API გასაღები, `.env`) git-ში არასდროს. `.gitignore` ძირითად შემთხვევებს ფარავს, ხელით commit-მდე კი staged ფაილები ასე შეგიძლია შეამოწმო (gitleaks v8.19 ან უფრო ახალი; exit 0 — სუფთაა, exit 1 — რაღაც იპოვა):

  ```bash
  gitleaks git --pre-commit --staged --redact
  ```

- force-push, უკვე ატვირთული ისტორიის გადაწერა და დესტრუქციული ბრძანებები (`rm -rf`, `git reset --hard`, `git clean -f`) აკრძალულია.
- ფაილს აგენტი მხოლოდ შენი თანხმობით წაშლის; `main`-ში წაშლა მხოლოდ მფლობელის მიერ დამტკიცებული PR-ით შედის.
