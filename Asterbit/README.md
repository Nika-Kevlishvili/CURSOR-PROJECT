# Asterbit — ჩვენი AI-native SDLC ძრავა

> **სტატუსი:** ძრავა v0. ჩონჩხი `main`-შია საერთო საფუძვლად; ADR-0001…0003 და PROCESS.md მფლობელის დამტკიცებას ელოდება. პროდუქტი ჯერ არ არჩეულა — მას Phase 1 (Intent) გადაწყვეტს.
> **თანამშრომლებისთვის:** დაიწყე [CONTRIBUTING.md](CONTRIBUTING.md)-ით — იქ წერია, რა დააყენო, როგორ ჩამოტვირთო და როგორ შეიტანო ცვლილება.

## რა არის ეს

წარმოიდგინე სამშენებლო კომპანია, რომელიც სახლს „თვალზე" არასდროს იწყებს. ჯერ შენთან ერთად აყალიბებს, როგორი სახლი გინდა. მერე ირჩევს მასალასა და კონსტრუქციას, აწესებს სამშენებლო მოედნის წესებს (ვინ სად შედის, რა არის აკრძალული), ხაზავს ნახაზს და ადგენს სამუშაო გრაფიკს. მშენებლობისას ოსტატი ყოველ სართულს ამოწმებს, ბოლოს კი ინსპექცია მთელ შენობას ამოწმებს და სიგნალიზაციასა და კამერებს დგამს.

ეს რეპოზიტორია (repository — პროექტის საქაღალდე, რომლის ისტორიასაც git ინახავს) ზუსტად ასეთ პროცესს აწყობს Cursor-ში, Claude-ის მოდელებთან მუშაობისთვის ([ADR-0008](docs/decisions/0008-cursor-support.md)). ამას SDLC ჰქვია (Software Development Life Cycle — პროგრამის სასიცოცხლო ციკლი, იდეიდან გაშვებამდე და შემდეგ მოვლამდე). ყოველი ეტაპი ერთი ჩაწერილი დოკუმენტით მთავრდება — ამას artifact ჰქვია (ეტაპის „ხელმოწერილი" შედეგი) — და შემდეგი ეტაპი სწორედ მისი წაკითხვით იწყება.

იდეა Anthropic-ის 2026 წლის აგვისტოს „AI-native SDLC playbook"-ს ეფუძნება: კოდის წერა აღარ არის ყველაზე ნელი ნაწილი, ამიტომ ხარისხი იქ წყდება, სადაც ადამიანი გადაწყვეტილებას იღებს — კარიბჭეებზე (gate — წერტილი, სადაც შენ ამტკიცებ ან აბრუნებ). Claude წერს, ამოწმებს და გთავაზობს; შენ წყვეტ.

სრული სამუშაო შეთანხმება — ვინ რას წყვეტს, როგორ მიდის სესია და რას სჭირდება შენი თანხმობა — [PROCESS.md](PROCESS.md)-შია. რა გაკეთდა და რა დარჩა, ამას [PROGRESS.md](PROGRESS.md) აჩვენებს.

**ერთი ცვლილება შენს თანმიმდევრობაში — რეკომენდაცია:** შეფასების (Phase 7) *დაგეგმვა* ჯობს Spec-ის შემდეგ მოხდეს, როცა უკვე ვიცით, რას ვაშენებთ, რათა კარიბჭეები გეგმაში მოხვდეს და კოდირებისას უკვე მუშაობდეს. *გაშვება* კი კოდირების დროს და გამოშვებამდე ხდება. ასე შენი პირობაც სრულდება — ვარიანტებს მაშინ შემოგთავაზებ, როცა იდეა და სხვა ეტაპები უკვე გავლილია — და შეცდომაც დროულად დაიჭირება. თუ გინდა, რომ ზუსტად შენი თავდაპირველი თანმიმდევრობით წავიდეთ, ერთი სიტყვით შევცვლი.

## ვინ რას აკეთებს — ორკესტრაციის პირველი ეტაპი

მთავარი კოდერია Sonnet 5.5 მაღალ effort-ზე (effort — რამდენ „ფიქრს" ხარჯავს მოდელი თითო ნაბიჯზე); Cursor-ში მას შენ ირჩევ მოდელის არჩევანში, სხვა მოდელის შემთხვევაში კი აგენტი გაგაფრთხილებს. Opus 5.5 ორ როლს ასრულებს. პირველი როლია მრჩეველი: დამხმარე აგენტი `advisor`, რომელსაც Sonnet გადამწყვეტ მომენტებში თავად ეკითხება — მიდგომის არჩევამდე, შეცდომის განმეორებისას და სანამ იტყვის „მორჩა". მეორე როლია აუდიტორი: ცალკე, სუფთა კონტექსტში ამოწმებს ყოველ კარიბჭესა და ყოველ ეტაპს, რათა ავტორმა საკუთარ ნამუშევარს ნიშანი თვითონ არ დაუწეროს.

ფაქტების სწრაფი მოძიება (ვერსია, ფასი, დოკუმენტაციის გვერდი) Haiku 5.5-ს აქვს მინდობილი — ესაა დამხმარე აგენტი `scout`, რომლის პასუხსაც უფრო ძლიერი მოდელი ამოწმებს. ძრავის ყველა როლს მხოლოდ Claude-ის მოდელები ასრულებს: ეს შენ გადაწყვიტე 2026-10-07-ს, როლების განაწილება (ვარიანტი A) კი 2026-10-08-ს აირჩიე. OpenAI-ისა და ღია მოდელების „მეორე ეტაპი" აღარ არის. დეტალები: [ADR-0007](docs/decisions/0007-claude-only-orchestration.md) და [ორკესტრაციის დიზაინი](sdlc/design/orchestration-and-loop.md).

## მეხსიერება ერთი აბზაცით

ყველა მეხსიერება ჩვეულებრივი markdown ფაილებია git-ში: მათი წაკითხვა შენც შეგიძლია და ისტორია არასდროს იკარგება. ნებისმიერი დამატებითი ინსტრუმენტი (ძიება, გრაფი) მხოლოდ ინდექსია ამ ფაილებზე, რომლის წაშლა და თავიდან აგება ნებისმიერ დროს შეიძლება. ყოველი შეკუმშვის შემდეგ (compaction — როცა საუბარი ძალიან დიდდება და Cursor მას მოკლე შეჯამებით ცვლის) handoff (გადაცემის ჩანაწერი) იწერება, სესიის ბოლოს — შეჯამება, დროდადრო კი ყველაფერი ერთ მოკლე „ახლანდელ მდგომარეობად" (`memory/now.md`) იკუმშება. ინტერვიუთი შევთანხმდით: შეკუმშვა 65%-ზე (Cursor-ში ამას ვერ ვაყენებთ — ის ფანჯრის ბოლოსთან კუმშავს), Obsidian-ის ვაულტი, ჯერ ჩვეულებრივი ძიება (QMD — მოგვიანებით, საჭიროებისას) და შეცვლილი აზრის კონტროლი ADR-ებით, git-ითა და სესიის ბოლოს შემოწმებით. დეტალები: [მეხსიერების დიზაინი](sdlc/design/memory-and-context.md), [ADR-0004](docs/decisions/0004-context-and-memory.md).

## რით დავიწყოთ

პირველ რიგში წაიკითხე ეს README, [PROCESS.md](PROCESS.md) (ჩვენი სამუშაო შეთანხმება), [docs/FILES.md](docs/FILES.md) (ყველა ფაილის ახსნა), [ძრავის შერჩევა](sdlc/research/engine-selection.md) და [მეხსიერების დიზაინი](sdlc/design/memory-and-context.md). მეხსიერების ინტერვიუ ჩატარდა, პრინციპები ჩაწერილია, harness აწყობილია: პარამეტრები და ავტომატური hook-ები (hook — ავტომატური ჩამრთველი, რომელიც განსაზღვრულ მომენტში თავისით ეშვება). საცდელი გაშვება სატესტო იდეაზე აღარ ტარდება (მფლობელი, 2026-10-08). შემდეგია Phase 0-ის კარიბჭე, მერე ნამდვილი პროდუქტი, როცა მფლობელი იდეას დაასახელებს.

## Cursor-ში მუშაობა

ძრავა Cursor-ში მუშაობს ([ADR-0008](docs/decisions/0008-cursor-support.md), ჯერ `proposed`): წესები `AGENTS.md`-შია, ბრძანებები (`/sdlc-*`), აგენტები და დაცვა — `.cursor/`-ში. 2026-10-08-მდე ძრავა Claude Code-ისთვის იყო აწყობილი; მისი ფაილები (`CLAUDE.md`, `.claude/`) წაიშალა მას შემდეგ, რაც Cursor-ის ალტერნატივა მზად იყო და შემოწმდა. სამი რამ განსხვავდება: მთავარ მოდელს (Claude Sonnet 5.5) ხელით ირჩევ და hook გაფრთხილებს, თუ სხვა მოდელი მუშაობს; მრჩეველი ჩაშენებული ხელსაწყოს ნაცვლად `advisor` აგენტია (Opus 5.5); და შეკუმშვის შემდეგ handoff-ს აგენტი თავად წერს, რადგან Cursor შეჯამებას hook-ს არ აჩვენებს. როგორ გახსნა Cursor-ში — [CONTRIBUTING.md](CONTRIBUTING.md) §3.
