# AI უსაფრთხოება — სტრუქტურა v0

> **სტატუსი:** მაღალი დონის ჩარჩო. კონკრეტული კონტროლები Phase 3-ში (Cursor-ის harness, [ADR-0008](../../docs/decisions/0008-cursor-support.md)) და Phase 8-ში (პროდუქტის AI უსაფრთხოება) შეირჩევა.

## 1. ორი დასაცავი ობიექტი

პირველი არის **Cursor-ის აგენტი, როგორც მშენებელი**. მას შენს ფაილებზე, ტერმინალსა და ინტერნეტზე აქვს წვდომა. თუ ის შეცდება ან მოტყუვდება (მაგალითად, ვებგვერდზე ჩამალული ინსტრუქციით), ზიანი შენს კომპიუტერზე მოხდება. მეორე არის **პროდუქტი**: თუ ის AI აგენტი იქნება, მას საკუთარი ხელსაწყოები, მონაცემები და მომხმარებლები ეყოლება.

## 2. ფენები — defense in depth (დაცვის რამდენიმე დამოუკიდებელი ხაზი)

| # | ფენა | რა ხდება | ტიპი | სად ცხოვრობს |
|---|---|---|---|---|
| L1 | უფლებები | allow / ask / deny წესები; ავტონომიის დონე | დეტერმინისტული | `.cursor/cli.json` (CLI); IDE-ში — Cursor-ის დასტურის რეჟიმი და L3 hook-ები |
| L2 | Sandbox | ფაილებისა და ქსელის იზოლაცია ოპერაციული სისტემის დონეზე; დომენების allowlist; საიდუმლოებების ჩამოცილება ბრძანებების გარემოდან | დეტერმინისტული | `.cursor/sandbox.json` (ჯერ არ არის — ცალკე გადაწყვეტილებაა) |
| L3 | Hook-ები | ყოველ მოქმედებაზე: დაბლოკვა, კითხვა ან ჩაწერა ჟურნალში | დეტერმინისტული | `.cursor/hooks.json` + `.cursor/hooks/` |
| L4 | Skills | პოლიტიკა ინსტრუქციის სახით | რჩევითი | `.cursor/skills/` |
| L5 | Review | `auditor` + `/security-review` ყოველ ეტაპზე | მოდელური | agents |
| L6 | მიწოდების ჯაჭვი | plugin-ების, skill-ებისა და MCP სერვერების შემოწმება ინსტალაციამდე (მაგ. SkillSpector), ვერსიების დაფიქსირება | შერეული | ADR-ები |
| L7 | პროდუქტის აგენტის კონტროლები | ხელსაწყოების allowlist, მინიმალური უფლებები, ადამიანის თანხმობა შეუქცევად მოქმედებებზე, ხარჯის ლიმიტი, kill switch | დეტერმინისტული + მოდელური | პროდუქტის კოდი |
| L8 | საიდუმლოებები | `.env` git-ის გარეთ, საიდუმლოებების მენეჯერი, სკანერები | დეტერმინისტული | git hooks, CI |
| L9 | დაკვირვება და ინციდენტი | ლოგები, განგაში, ინციდენტი → ახალი eval | შერეული | Phase 9 |

playbook-ის მთავარი გაკვეთილი აქ ასეთია: skill დარღვევას იშვიათს ხდის, hook კი — თითქმის შეუძლებელს. ის, რაც ყოველთვის უნდა სრულდებოდეს, დეტერმინისტულ კონტროლზე უნდა იდგეს და არა მხოლოდ ინსტრუქციაზე. ასევე: tool-ის დონის აკრძალვა (მაგ. WebFetch-ზე) shell-ის ბრძანებას ქსელში გასვლაში ვერ შეუშლის ხელს — ამას მხოლოდ sandbox-ის ქსელური allowlist აკეთებს.

## 3. საფრთხეების კატალოგი

საფუძველი: OWASP Top 10 for LLM Applications (2025) + აგენტებისთვის დამახასიათებელი რისკები.

| საფრთხე | მარტივად | ძირითადი კონტროლი |
|---|---|---|
| Prompt injection | უცხო ტექსტში (ვებგვერდი, ფაილი, ელფოსტა) ჩამალული ბრძანება | უცხო შინაარსი მონაცემია და არა ინსტრუქცია; მეხსიერების „ღობე" (`.cursor/hooks/untrusted.py`); მინიმალური უფლებები |
| Sensitive information disclosure | საიდუმლოების ან პერსონალური მონაცემის გაჟონვა | `.env*`-ის კითხვის აკრძალვა; sandbox-ის credentials წესები; ლოგებში რედაქცია |
| Supply chain | მავნე plugin, skill, MCP სერვერი ან პაკეტი | ინსტალაციამდე შემოწმება; ვერსიების ფიქსაცია; SkillSpector |
| Data / model poisoning | მავნე მონაცემი სასწავლო მასალაში ან RAG-ის ინდექსში | წყაროების კონტროლი; ინდექსი მხოლოდ ჩვენი ფაილებიდან |
| Improper output handling | მოდელის პასუხი პირდაპირ shell-ში, SQL-ში ან HTML-ში ხვდება | ვალიდაცია; პარამეტრიზებული მოთხოვნები; escaping |
| Excessive agency | აგენტს მეტი შეუძლია, ვიდრე სჭირდება | allowlist; ადამიანის თანხმობა; ავტონომიის დონეები |
| System prompt leakage | ინსტრუქციების ან საიდუმლოებების გამოჩენა პასუხში | საიდუმლოება prompt-ში არასდროს იწერება |
| Vector & embedding weaknesses | RAG-ის ინდექსიდან სხვისი მონაცემის ამოღება | ინდექსზე წვდომის კონტროლი |
| Misinformation | დამაჯერებელი, მაგრამ მცდარი პასუხი | წყაროს მითითება; evals; „არ ვიცი"-ს თქმის უფლება |
| Unbounded consumption | უსასრულო ციკლი ან ხარჯის აფეთქება | ბიუჯეტები; `maxTurns`; rate limit |
| Memory poisoning (აგენტური) | მეხსიერებაში ჩამალული ინსტრუქცია ყოველ სესიაზე ხელახლა იტვირთება | მეხსიერებაში მხოლოდ Claude-ის საკუთარი შეჯამებები; ცვლილებების განხილვა git-ის diff-ში |

## 4. რას ვიღებთ playbook-იდან და რას არა

- ✅ საიდუმლოებებისა და ქსელის deny-სია; „უსაფრთხო შიდა ციკლის" (test, lint, build) allowlist, რომ მუდმივმა კითხვებმა არ დაგღალოს; hook-ები, რომლებიც ბლოკის მიზეზს და დამტკიცების გზას ხსნიან; sandbox ქსელის allowlist-ით.
- ✅ პრინციპი: აგენტი production-ის კარიბჭემდე მიდის და არა მის იქით.
- ⏸ managed settings (MDM), Claude Security (Enterprise), Claude Tag — ორგანიზაციული ფუნქციებია. მარტოხელა მფლობელისთვის ალტერნატივა: პროექტის settings + გლობალური hook-ები (უკვე გაქვს) + `/security-review`.

## 5. რა გაქვს უკვე გლობალურად (`~/.claude/settings.json`-დან, შემოწმდა 2026-10-06 — Claude Code-ის ეპოქა; Cursor ამ hook-ებს მხოლოდ Third-Party Imports-ით უშვებს, CONTRIBUTING.md §3)

PreToolUse-ზე: `audit-log`, `destructive-blocker` (წაშლა + მონაცემების გატანა), `secret-detection`, `sensitive-file`, `scope-guard` (მხოლოდ გაფრთხილება), `token-warnings`, `dev-server`. PostToolUse-ზე: `auto-format`, `auto-lint`, `file-backup`, `console-log-warning`. Phase 3-ში დავადგენთ, რა უნდა დაემატოს პროექტის დონეზე და როგორ დავწვრთნათ თითოეული.
