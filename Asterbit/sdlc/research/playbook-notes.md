# Anthropic — „The AI-native SDLC playbook": შესწავლის ჩანაწერები

> წყარო: [claude.com/blog/the-ai-native-sdlc-playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) · ავტორი: Louis Claxton · 2026-08-21. ქვემოთ ჩემი შეჯამება და ანალიზია ჩვენი ძრავისთვის — ორიგინალის ტექსტი არ არის. სრული ვერსიისთვის წაიკითხე თავად სტატია (PDF-ადაც ჩამოიტვირთება).

## 1. მთავარი აზრი

სტატიის ცენტრალური თეზისი ასეთია: კოდის წერა აღარ არის „ბოთლის ყელი". აგენტები კოდს საათებში წერენ, მაგრამ მის გარშემო არსებული პროცესები — დაგეგმვა, review, ტესტირება, გაშვება — ისევ ადამიანის სიჩქარით მიდის. ძველი კონტროლები (ყოველი ხაზის ხელით განხილვა, ყოველკვირეული კომიტეტები) აგენტის გამომუშავებას ვერ ეწევა. ამიტომ ისინი უნდა გადაიქცეს მანქანურად აღსრულებულ კონტროლებად. თუმცა განსჯის მოთხოვნილ ყოველ გადაწყვეტილებაზე პასუხისმგებლობა ადამიანს რჩება; იცვლება მხოლოდ ის, სად არის მისი ყურადღება — კარიბჭეებზე.

## 2. ექვსი ეტაპი, როგორც წრე

Plan → Design → Build → Test → Deploy → Maintain, ხოლო Maintain ისევ Plan-ს კვებავს. ყოველი ეტაპი მთავრდება git-ში ჩაწერილი არტეფაქტით (intent.md, spec.md, plan.md, diff და ტესტები, PR და მისი review-ს შედეგები, ინციდენტის ჩანაწერი), შემდეგი ეტაპი კი სწორედ მისი წაკითხვით იწყება. commit-ების ჯაჭვი ერთდროულად audit trail-იცაა: ვინ რა მოითხოვა, რა გააკეთა აგენტმა და ვინ დაამტკიცა. სტატია გვირჩევს ჯერ ყველა ნაბიჯი ხელით გავუშვათ, საბოლოო მიზანი კი ისაა, რომ ყოველი დამტკიცებული არტეფაქტი შემდეგ კარიბჭეს ავტომატურად რთავდეს.

## 3. „Play"-ის სტრუქტურა და როგორ გადმოვიტანეთ

სტატიაში ყოველი პრაქტიკა („play") ერთნაირადაა აგებული: რა იცვლება; რა არის წინაპირობა და რა ინფრასტრუქტურაა საჭირო; ნაბიჯები; მმართველობა (რა აღსრულდება, რა არის მტკიცებულება, სად იწერება, ვინ ამტკიცებს); და გაზომვა წინმსწრები და შედეგობრივი ინდიკატორებით. play-ებს შორის დამოკიდებულებების გრაფია: ჯერ ის ინერგება, რასაც წინაპირობა არ აქვს.

ჩვენთან ყოველ skill-ს აქვს „Before you start" (წინაპირობა და კარიბჭე), ნაბიჯები და „Done when"; მმართველობას აუდიტორი ამოწმებს, გაზომვა კი [დაკვირვების დიზაინშია](../design/ai-observability.md).

## 5. რისი მორგება გვჭირდება მარტოხელა მფლობელისთვის

playbook გუნდებს და როლებს ვარაუდობს: პროდუქტის მფლობელი, tech lead, პლატფორმის ინჟინერი, უსაფრთხოების ხელმძღვანელი. ჩვენთან ადამიანური როლები შენ გაერთიანებულია; ანალიტიკოსისა და ინჟინრის როლს Claude ასრულებს, review-ს — აუდიტორი. მოვალეობების გამიჯვნა ასე ნარჩუნდება: ავტორი და აუდიტორი სხვადასხვა აგენტია, საბოლოო დამტკიცება კი შენია. საწარმოს ფუნქციებს (MDM, Claude Security, Code Review სერვისი, Claude Tag) უფრო მსუბუქი ეკვივალენტები ცვლის.

## 6. საზომები, რომლებსაც git-იდან დავთვლით

- დრო intent → spec → plan commit-ებს შორის.
- spec-ის commit-ები პირველი plan-ის commit-ის შემდეგ (გადაკეთება).
- დავალებების წილი, რომლებიც პირველივე CHECK-ზე მწვანდება.
- განმეორებული გაკვეთილები (ერთი და იგივე შეცდომა ორჯერ).
- აუდიტორის ხარვეზების ტენდენცია კარიბჭეების მიხედვით.
